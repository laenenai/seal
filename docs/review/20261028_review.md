## How this review was produced

Nine read-only reviewer agents worked in parallel, one per dimension: Go/API, code cleanliness, architecture, security/cryptography, developer experience, testing, long-term maintainability/release, documentation, and an extra cryptographic-format/specification review. Overlapping panel findings were merged under one stable ID per issue; cross-references are used where a finding has more than one dimension.

The external consumer probe reproduced four material behaviours:

- A reader whose `Stat`/`Seek` yields a negative remaining length caused `NewRecordReader` to read the entire 1,099,533-byte record before returning `max ciphertext exceeded`, instead of failing closed with `ErrUnknownLength`.

## Executive summary

**Is this production grade today? No.** The cryptographic construction is thoughtful and the test suite is better than most early-stage crypto libraries, but the module is not yet safe to adopt for production data. The code is closer to production-grade than the project around it: the release/security process is not yet credible for a cryptographic dependency, and two resource-control paths fail open.

The five things that matter most:

1. **Fix the fail-open length/allocation paths in `NewRecordReader`.** A negative derived length switches the reader to an unbounded `io.ReadAll`, and a declared length is allocated before the plaintext ceiling is checked. These defeat the module's own "fail closed / before allocation" security rules. (SEC-02, SEC-03)
2. **Stand up a real security and release process.** Private vulnerability reporting is disabled on the GitHub repository, no GitHub releases exist for the tags, tags are unsigned, `main` is unprotected, there is one maintainer, and SEAL2 has had no external cryptographic review. For a crypto library this is the largest adoption blocker. (SEC-01, MAINT-01, MAINT-02, MAINT-04, MAINT-06; Q2, Q6, Q7)
3. **Clean the public API before v1.0.** Type aliases expose internal AAD encoding and methods returning an unnameable `domain.Resolved`, the retired `api.txt` golden file pinned internal declarations consumers cannot import, and several exported constants/sentinels have no public operation. `go doc` hides the fields and methods that make `Limits` and the address types usable. (GO-01, ARCH-01, ARCH-04, DX-03)
4. **Strengthen the conformance suite and fuzzing.** The suite can certify an implementation that provides integrity but not confidentiality; it checks invalid DEKs only on `EncryptRecord`; it does not constrain ranged-read I/O cost; and there are no fuzz targets. "CAS passed the suite" is therefore a narrower claim than the docs imply. (TEST-01, TEST-02, TEST-03, TEST-05)
5. **Make documentation and tooling tell the truth.** The README still describes v0.1.0 as current, test counts disagree (24 vs 23), "no partial result" is false for the streaming reader, the quickstart cannot be copied, and the formatter requires two passes under gofumpt 0.12 while CI duplicates the mise pins. (DOC-01, DOC-05, DOC-06, DX-01, DX-04, DX-05)

## Findings

Severity definitions: **BLOCKER** = must fix before any production use; **MAJOR** = should fix before external adoption or v1.0; **MINOR** = worthwhile; **NIT** = polish.

### Go best practices and API shape

#### GO-01 — `Limits.Resolve*` returns an unnameable internal `domain.Resolved`
**Severity:** MAJOR · **Breaking:** Yes if removed · **Effort:** S/M

**Evidence:** `seal.go:148` aliases `Limits = domain.Limits`; `internal/domain/limits.go:88` exposes `func (l Limits) ResolveCompact() (Resolved, error)`; the retired `api.txt:186-188` recorded the method, but `seal` never aliases `Resolved` and no public entry point accepts it. `go doc github.com/laenenai/seal.Limits` shows only the alias, no fields.

**Why it matters:** A consumer can call `seal.Limits{}.ResolveCompact()` and hold the result with `:=`, but cannot name its type in a field, parameter, or return value, and cannot pass it to anything public. This is unusable surface that still enters the compatibility promise. It also hides the actual fields (`MaxPlaintext`, `MaxCiphertext`) from `go doc`.

**Recommended change:** Prefer removing `ResolveCompact`/`ResolveFramed` from the alias surface: move limit resolution to an internal function or a small `internal/limits` package, keep `Resolved` internal, and leave `seal.Limits` as documented data. If pre-resolution is genuinely intended as public API, alias `Resolved` and document it. Do not leave the half-exposed state. Run `mise run api-diff` against the last tag after the cleanup.

#### GO-02 — Allocation hot spots in both formats; no benchmarks
**Severity:** MINOR · **Breaking:** No · **Effort:** M

**Evidence:** `internal/framed/framed.go:87-91` allocates a nonce per frame; `:116-127` allocates an AAD slice per frame; `:393-397` allocates a full ciphertext buffer per frame; `internal/compact/compact.go:112-115` calls `addr.String()` and under-sizes the AAD buffer (`len(prefix)+8+len(addr.String())` omits the count and per-part prefixes); `seal.go:427` uses `io.ReadAll` for `DecryptObject` despite knowing an upper bound from `len(ciphertext)`.

**Why it matters:** A 1 GiB stream performs roughly 1,000 unnecessary ~1 MiB allocations plus two small allocations per frame. Compact records are the "tens of millions of short values" path, where a per-record capacity under-estimate and a joined-string allocation are measurable. There are no benchmarks pinning allocations, so regressions are invisible.

**Recommended change:** Store reusable nonce/AAD/wire scratch buffers on the writer/reader/range reader; rebuild into `[:0]`; pre-size `DecryptObject` to `len(ciphertext)`; compute the record-AAD capacity exactly or let `AppendAAD` grow without `String()`. Add benchmarks for seal/open, sequential open, ranged open, and compact open, including `AllocsPerRun`.

#### GO-03 — `DEK` aliasing couples seal's API to a pre-1.0 dependency
**Severity:** MINOR · **Breaking:** No for a boundary test; Yes for a seal-owned type · **Effort:** S/L

**Evidence:** `seal.go:135` `DEK = keyring.DEK`; `go.mod:5` requires `keyring v0.2.0`; the retired `api.txt:20` recorded the alias but not keyring's method set. `go mod graph` expands to 55 module edges because keyring's requirements include testcontainers and its transitive set.

**Why it matters:** The alias is a defensible ownership decision, but it means seal's effective public type, validation semantics, rendering, and release cadence are keyring's. A keyring v0.x release can remove `Bytes`, `Validate`, `Destroy`, `Format`, or `LogValue` without seal's API golden file noticing. A `seal v1` cannot be more stable than `keyring v0`.

**Recommended change:** Keep the alias if the zeroization/redaction rationale is retained, but add a boundary contract test that pins the method set and security-relevant behaviour of `seal.DEK`; gate seal v1.0 on keyring v1 or an explicit compatibility statement. Ask keyring to move test-only dependencies out of its main `require` block. The alternative—a seal-owned key type/interface converted at the boundary—is a much larger break and forfeits keyring's hardening.

#### GO-04 — `sealtest.NewDEK` takes `*testing.T` instead of `testing.TB`
**Severity:** NIT · **Breaking:** No · **Effort:** S

**Evidence:** `sealtest/suite.go:869` `func NewDEK(t *testing.T) seal.DEK`. The function uses only `Helper`, `Fatalf`, and `Cleanup`, all available on `testing.TB`.

**Why it matters:** The narrower parameter prevents use from benchmarks and fuzz targets for no benefit. Suite helpers that call `t.Run` legitimately need `*testing.T`; the fixture does not.

**Recommended change:** Change the parameter to `testing.TB` and add a compile-only benchmark/example use.

### Code cleanliness

#### CLEAN-01 — The facade holds one-shot logic, contradicting its own contract
**Severity:** MINOR · **Breaking:** No · **Effort:** S

**Evidence:** `seal.go:105-106` says "every function here is a short forward to an internal package. It holds no logic beyond resolving a Limits once at the boundary." Yet `seal.go:388-435` implements buffer sizing, writer lifecycle, `io.ReadAll`, and read/close error ordering for `EncryptObject`/`DecryptObject`. `internal/compact/compact.go:124-213` has the analogous `Seal`/`Open`; `internal/framed` has no one-shot equivalent.

**Why it matters:** The stated architecture rule is false, and framed's one-shot semantics live where framed's own tests cannot reach them directly. A future port implementation must reimplement those semantics from the conformance suite.

**Recommended change:** Move the framed one-shot implementation into `internal/framed` as `Seal`/`Open`, mirroring compact; let `seal.go` resolve, check, and forward.

#### CLEAN-02 — Four render methods are copied onto five returned types
**Severity:** MINOR · **Breaking:** No · **Effort:** S

**Evidence:** `internal/framed/framed.go:297-302`, `:495-500`, `:586-591`; `internal/compact/compact.go:290-295`, `:387-392` each implement `String`, `Format`, `MarshalJSON`, and `LogValue` with the same body.

**Why it matters:** Twenty near-identical methods encode one security policy. Adding a returned type or changing the JSON quoting requires four edits per type, and `slog.LogValuer` is easy to forget. The conformance suite catches omissions, but centralizing removes the chance.

**Recommended change:** Add one internal `redacted` helper type with a name field implementing all four interfaces, embed it in each returned type, and initialize it with `"seal.EncryptWriter"`, etc. Method sets are preserved by promotion.

#### CLEAN-03 — `.golangci.yml` enforces boundaries for packages that do not exist
**Severity:** MINOR · **Breaking:** No · **Effort:** S

**Evidence:** `.golangci.yml:36-44` configures an `internal/obs` OTel metric boundary; `:51` excludes `cmd/<binary>` files; `:5-18` includes DB/HTTP linters (`bodyclose`, `rowserrcheck`, `sqlclosecheck`, `contextcheck`, `noctx`). The repository has no `internal/obs`, no `cmd/`, no database, and no OTel dependency. The `forbidigo` message at `:23` says "use structured logging" although the library deliberately has no logger.

**Why it matters:** Dead gates teach contributors that red output is normal and imply an architecture the module does not have. The `cmd/` exclusion pre-authorizes `panic` in a path that does not exist.

**Recommended change:** Remove `depguard`, its settings, and the exclusions block; prune the DB/HTTP linters until that code exists; keep `errcheck`, `govet`, `staticcheck`, `revive`, `gosec`, `gocritic`, `errorlint`, `forbidigo`.

#### CLEAN-04 — `mise run generate` is a guaranteed failure and the task descriptions are stale
**Severity:** MINOR · **Breaking:** No · **Effort:** S

**Evidence:** `mise.toml:15` pins `sqlc = "1.30.0"`; `mise.toml:47-59` defines `generate = "sqlc generate"`. There is no `sqlc.yaml` or `db/` tree; the command fails (`sqlc.(yaml|yml) or sqlc.json: file does not exist`). `mise.toml:35` describes `build` as proving "the shipped binary" is cgo-free although this module ships no binary; `:39` describes `test-all` as including "container- and database-backed tests" although there are none.

**Why it matters:** The file's own comment says "a task list with dangling entries trains people to ignore task lists," and this is exactly such an entry. Every developer installs an unused `sqlc`.

**Recommended change:** Delete `generate` and the `sqlc` pin until a `sqlc.yaml` exists; correct the `build`/`test-all` descriptions. Add the task and pin back with the first actual generated package.

#### CLEAN-05 — HKDF/AES-GCM construction is duplicated across both formats
**Severity:** MINOR · **Breaking:** No · **Effort:** M

**Evidence:** `internal/framed/framed.go:71-80` does `deriveFrameKey` → `aes.NewCipher` → `cipher.NewGCM`; `internal/compact/compact.go:83-96` repeats the same `dek.Validate` / `aes.NewCipher` / `cipher.NewGCM` sequence with an extra nonce return.

**Why it matters:** This is security-critical plumbing copied across two packages. A future check, algorithm change, or error-wrapping fix applied to one copy silently leaves the other behind.

**Recommended change:** Add a small `internal/aead` helper (not in `internal/domain`, whose documented invariant is that it does not touch ciphers) that takes the DEK, salt, info string, and derived length and returns the AEAD and optional nonce. Each format supplies only its domain constants.

#### CLEAN-06 — Essayistic comments duplicate docs and already drift
**Severity:** NIT · **Breaking:** No · **Effort:** S/M

**Evidence:** `seal.go:1-114` is a 114-line package comment (269 of the file's 495 lines are comments); `seal.go:98-106` contains the false "holds no logic" statement; `internal/framed/framed.go:93-115` is a 23-line comment on a 12-line function. The "two mechanisms" rationale is repeated at `framed.go:144-156`, `seal.go:166-170`, `internal/domain/format.go:112-122`, and `internal/domain/limits.go:13-16`.

**Why it matters:** README, CHARTER, `docs/format.md`, and CONVENTIONS already own this prose. Duplication has already produced a false statement and makes review diffs noisy.

**Recommended change:** Cut the facade package comment to roughly 25-35 lines (what it does, the two shapes, ceilings, no key management, links); move extraction history to CHARTER; keep invariant comments next to the code; delete repeated rationale from all but one home.

### Architecture and internal consistency

#### ARCH-01 — The public surface is an unpruned view of `internal/domain`
**Severity:** MAJOR · **Breaking:** Yes · **Effort:** M

**Evidence:** `seal.go:159-174` re-exports `VersionFramed`, `VersionCompact`, `FrameSize`, `MinFrameSize`, `MaxFrameSize`; `seal.go:207-208` re-exports `ErrInvalidFrameSize`, which `internal/domain/errors.go:68-70` says is "Reachable only through that package's test-only seam today"; `internal/domain/address.go:119` and `:187` expose `AppendAAD`, publishing the exact wire AAD encoding; `api_test.go:37-41` includes all of `internal/domain` in the golden file, including declarations consumers cannot import (`DerivableLength`, `ValidateStreamCeiling`, `CompactCiphertextLen`, `NewObjectAddress`).

**Why it matters:** Every change to an internal helper or constant becomes a compatibility break even when no consumer-facing operation exists. `Version` is accepted or returned by no seal function; `MinFrameSize`/`MaxFrameSize`/`ErrInvalidFrameSize` are decoder/test-seam facts; `AppendAAD` lets consumers build against bytes the format owner may need to evolve. The golden file both over-pins internal cleanup and under-pins the alias method sets that consumers actually see.

**Recommended change:** Define the public set deliberately and review the reachable surface of `seal` and `sealtest` with `mise run api-diff`, expanding aliases to their exposed method sets. Unexport `AppendAAD` and use package-level `domain.AppendObjectAAD`/`AppendRecordAAD` inside the format packages. Remove `Version*`, `MinFrameSize`, `MaxFrameSize`, and `ErrInvalidFrameSize` unless paired with a real operation. Keep `FrameSize`, `CompactOverhead`, `DefaultMaxPlaintext`, `Unlimited`, and `Redacted`.

#### ARCH-02 — The conformance suite requires a frame size the port never promises
**Severity:** MINOR · **Breaking:** No for docs · **Effort:** S

**Evidence:** `sealtest/frames.go:186-189` says frame size "is seal.FrameSize, which is what the port's own documentation says an encoder writes"; `seal.go:236-255`'s `StreamSealer` documentation says no such thing. `sealtest/frames.go:238-256` measures against `seal.FrameSize`, and `sealtest/suite.go:98` uses `seal.FrameSize` boundaries.

**Why it matters:** An alternative `StreamSealer` that frames at 64 KiB satisfies the interface but fails `measureFramedGeometry`. The suite is therefore a de facto format-1 implementation test, which is fine only if the contract says so.

**Recommended change:** State the `FrameSize` requirement on `StreamSealer` and `NewEncryptWriter`, or add a suite option such as `RunStreamSealerSuiteWithFrameSize` defaulting to `seal.FrameSize`.

#### ARCH-03 — `internal/domain` is both the shared kernel and the wire-format registry
**Severity:** MINOR · **Breaking:** No for internal restructure · **Effort:** M

**Evidence:** `internal/domain/errors.go:1-6` defines the package as "the single home for every value object"; `internal/domain/format.go:84-165` holds both formats' magic, HKDF info, header/prefix/salt/tag sizes, frame bounds, and overhead; `internal/domain/limits.go:196-242` implements `DerivableLength`, used only by compact.

**Why it matters:** Adding or changing a format touches `domain`, that format's package, the facade, and the docs. The dependency direction is acyclic, but format details should live with the format that owns them.

**Recommended change:** Keep addresses, limits, errors, and the `Version` registry in `domain`; move framed layout constants into `internal/framed` and compact layout constants into `internal/compact`; move `DerivableLength` beside compact or into a small helper package.

#### ARCH-04 — No consumer-facing ciphertext-sizing or format-identification contract
**Severity:** MINOR · **Breaking:** Additive; Yes if `Version` is removed · **Effort:** S/M

**Evidence:** `internal/domain/format.go:167-184` has `CompactCiphertextLen`/`FramedCiphertextLen`; `seal.go:176-178` exposes only `CompactOverhead`; `seal.go:153-162` exposes `Version` constants but no seal function accepts or returns a `Version`. `docs/format.md:70-73` says a compact record is not identifiable by inspection.

**Why it matters:** Consumers sizing a column or an HTTP response must reimplement framed arithmetic, including the "one tag generous at exact multiples" quirk. Consumers storing both formats have a public `Version` type but no supported way to record or route it, inviting bespoke version columns.

**Recommended change:** Expose `FramedCiphertextLen`/`CompactCiphertextLen`, or one `CiphertextLen(v Version, n int64)`; either add `VersionOf(ciphertext []byte) (Version, bool)` explicitly documented as unauthenticated identification, or remove `Version` from the facade and state that format is caller metadata. Do not keep both half-measures.

#### ARCH-05 — The anti-relocation premise is not on the public constructors
**Severity:** MINOR · **Breaking:** No · **Effort:** S

**Evidence:** `docs/format.md:320-350` states that "a consumer whose object addresses are not unique per tenant has a splicing exposure seal cannot close for it." `seal.go:217-234` documents only invalid/unsafe components; `internal/domain/address.go:124-131` says order is significant but not that addresses must be unique and stable. The range reader's authoritative-`size` obligation, by contrast, is on the public method at `seal.go:355-366`.

**Why it matters:** The module's central claim—relocation is a decryption failure—is conditional on consumers passing unique, stable components. pkg.go.dev readers see the constructor docs, not `docs/format.md`. A consumer that passes a display name, mutable path, or truncated content address gets no warning where the mistake is made.

**Recommended change:** Put the uniqueness/stability obligation in the godoc for `NewObjectAddress` and `NewRecordAddress`, in the package doc's "property that matters" section, in README, and in SECURITY.md. Use the range reader's authoritative-`size` wording as the model.

### Security and cryptography

#### SEC-01 — Private vulnerability reporting is disabled
**Severity:** BLOCKER · **Breaking:** No · **Effort:** S

**Evidence:** `SECURITY.md:5-7` says to report privately through GitHub's private vulnerability reporting. `gh api repos/laenenai/seal/private-vulnerability-reporting` returns `{"enabled":false}`. `SECURITY.md` has no email/PGP fallback, no supported-version table, and no acknowledgement or disclosure timeline.

**Why it matters:** A cryptographic library whose only documented disclosure route is switched off pushes researchers toward public issues, private silence, or abandonment. There is no predictable embargo or response commitment.

**Recommended change:** Enable GitHub private vulnerability reporting; add a monitored security email/PGP fallback; add a supported-versions table and acknowledgement/triage/disclosure targets; document the advisory and credit process; exercise the flow before announcing production adoption.

#### SEC-02 — `NewRecordReader` fails open on a negative derived length and ignores trailing bytes
**Severity:** BLOCKER · **Breaking:** No · **Effort:** S

**Evidence:** `internal/domain/limits.go:222` returns `info.Size() - cur, true` and `:240` returns `end - cur, true` without checking for a negative result; `internal/compact/compact.go:337-345` stores that negative value and calls `CheckCiphertext`, which passes because `n > Max` is false for negatives; `:362-363` then treats any negative `declared` as "no declared length" and calls `io.ReadAll`. A probe reader with `size-cur = -490` caused the whole 1,099,533-byte record to be read before `ErrLimitExceeded`. Separately, a reader whose `Len` under-reports its data was accepted with 24 trailing, unauthenticated bytes silently ignored.

**Why it matters:** This directly defeats the module's "fail closed on an unknown length" rule and allows an unbounded read/DoS under the default ceiling. The trailing-data case means the authenticated region can be only a prefix of what the caller supplied, contrary to "the single compact record in `r`."

**Recommended change:** Make `DerivableLength` return `(0,false)` for any negative result; make `NewRecordReader` reject `n < 0` as `ErrUnknownLength` (or `ErrCorrupt` for a malformed source); keep `declared == -1` as an explicit "unbounded" sentinel only when `!limits.Bounded()`; require EOF after the declared bytes or explicitly document and test that a suffix is ignored. Add conformance cases for negative and lying length readers.

#### SEC-03 — `NewRecordReader` allocates from an untrusted declared length before enforcing `MaxPlaintext`
**Severity:** MAJOR · **Breaking:** No · **Effort:** S

**Evidence:** `internal/compact/compact.go:336-348` checks only `CheckCiphertext(n)` before `readAll`; `:369` does `buf := make([]byte, declared)`; the plaintext ceiling is checked inside `Open` at `:194`, after the read. With `Limits{MaxPlaintext: 1024, MaxCiphertext: Unlimited}`—a configuration the docs explicitly say is supported—a reader that declares a 1 TB record causes a 1 TB allocation. A probe with a declared 10 MiB read all 10,485,760 bytes before returning `max plaintext exceeded`.

**Why it matters:** This is the allocation-bomb pattern the five-rule design says it prevents. `Open`'s later recheck prevents acceptance, not resource consumption. A sparse file, object-store reader, or lying `Len()` is enough.

**Recommended change:** Before `readAll`, if `MaxPlaintext` is finite, reject `declared > MaxPlaintext + CompactOverhead` (with an overflow guard); or cap the allocation by `min(MaxCiphertext, MaxPlaintext+overhead)`. Enforce the plaintext ceiling against the declared length itself, not only after reading.

#### SEC-04 — Derived keys and plaintext are never zeroized; the boundary is undocumented
**Severity:** MINOR · **Breaking:** No · **Effort:** M

**Evidence:** `internal/framed/framed.go:62-66` returns the HKDF key; `:76` only copies it into the AES schedule; `:181,186,329` retain `cipher.AEAD` and plaintext buffers. `internal/compact/compact.go:79` returns slices of the HKDF output; `:230,305` retain plaintext. There is no `clear`, `Destroy`, or release on `Close`. `seal.go:129-130` calls the DEK "zeroizable and non-rendering," but the docs never say the derived material is not.

**Why it matters:** `defer dek.Destroy()` wipes only keyring's DEK. Derived frame/record keys, AES key schedules, and decrypted plaintext remain reachable on the heap after `Close`/EOF; a core dump, heap profile, debug endpoint, or GC-reused page can disclose them. Redaction only prevents formatting-based leaks, not memory disclosure.

**Recommended change:** Best-effort zeroize `key`/`okm` immediately after `aes.NewCipher`; `clear` and nil plaintext buffers on `Close`/EOF; drop the `cipher.AEAD` reference after `Close`. Document that Go cannot guarantee wiping the AES schedule via the standard API, or use an available secret-memory mechanism. State the boundary explicitly in SECURITY.md and the package doc. Add a test that a closed writer/reader no longer retains the plaintext buffer.

#### SEC-05 — Range-reader size arithmetic is unguarded and the G115 suppressions are only conditionally sound
**Severity:** MINOR · **Breaking:** No · **Effort:** S

**Evidence:** `internal/framed/framed.go:656` computes `numFrames := (cipherTotal + wireFrameSize - 1) / wireFrameSize`; `:657` computes `lastFrameCipherLen`; `:567` computes `frameOff := int64(domain.FramedHeaderSize) + i*r.wireFrameSize`; `:575,577` convert `int64(i)` to `uint64` under `//nolint:gosec // frame index is bounded by stream size`. `numFrames` is derived from caller-supplied `size` without an overflow guard. The docs at `docs/format.md:428-432` acknowledge the missing guard; depending on `frame_size`, a size near `MaxInt64` can overflow the frame-count arithmetic or be accepted, rather than being rejected before computation. The `//nolint` comments are golangci-lint directives, not gosec ones; standalone gosec still reports all five findings.

**Why it matters:** If the arithmetic wraps, the index/nonce domain is wrong (authentication fails, not a memory-safety escape), but malformed/oversized sizes can still produce confusing errors or resource use. The suppressions hide the conversions from a standalone gosec gate while the code relies on an undocumented caller contract.

**Recommended change:** Add a checked maximum for `size` (or reject sizes above a sane ceiling), use checked arithmetic/`math/bits` for `numFrames`, `lastFrameCipherLen`, and `frameOff`, and make the conversions explicitly guarded rather than suppressed. If standalone gosec is a gate, use `// #nosec G115` with the reason or fix the code; otherwise do not claim gosec is clean.

#### SEC-06 — GCM hard limits are not enforced; `Unlimited` can panic and the 2^64-frame claim exceeds the per-key budget
**Severity:** MINOR · **Breaking:** No for realistic data · **Effort:** S/M

**Evidence:** `internal/compact/compact.go:145` accepts any plaintext length allowed by `Limits`, including `Unlimited`; `:160` passes it to `aead.Seal`. `internal/framed/framed.go:242` increments a `uint64` frame index with no per-key invocation cap. `docs/format.md:655-660` states GCM's 2^39−256-bit per-invocation limit and claims a stream is bounded at 2^64 frames (2^84 bytes at 1 MiB). Go 1.27's GCM panics for plaintexts above `(2^32-2)*16` bytes.

**Why it matters:** `EncryptRecord`/`NewRecordWriter` with `Limits{MaxPlaintext: Unlimited}` can reach a stdlib panic instead of a typed `LimitError`. A 2^64-frame stream is a nonce-counter bound, not a GCM per-key data bound; NIST guidance limits total protected blocks per key to about 2^64, which 2^84 bytes exceeds. The docs present the lower bound as the format limit.

**Recommended change:** Enforce a hard compact plaintext maximum (the GCM per-invocation limit) in `Seal`/`NewWriter`, and a framed maximum frame count/stream size consistent with the per-key invocation budget; return `ErrLimitExceeded`/`ErrInvalidLimit`, not panic. Correct `docs/format.md` to distinguish nonce uniqueness from the per-key block budget, and document key rotation for very large streams.

#### SEC-07 — Address validation admits Unicode bidi/format controls and does not canonicalize
**Severity:** MINOR · **Breaking:** Yes for callers using such characters · **Effort:** S

**Evidence:** `internal/domain/address.go:234-237` rejects `unicode.IsControl` and `unicode.IsSpace`, but `unicode.IsControl` covers category Cc, not Cf. U+202E RIGHT-TO-LEFT OVERRIDE, U+200E/200F marks, U+2066-2069 isolates, zero-width joiners, and noncharacters pass validation. `String()` at `:107` and `:174` renders addresses directly. No NFC/NFD normalization is applied.

**Why it matters:** Addresses are logged and may reach database/object-store keys. A tenant/object containing U+202E can visually reorder an audit line; zero-width characters can make two distinct identities look identical. No normalization means a producer and consumer using different normalization get a decryption failure or treat visually identical IDs as distinct. This contradicts the "safe set is the intersection" rationale in the same file.

**Recommended change:** Restrict to a conservative ASCII set (alphanumerics plus colon, hyphen, dot) or explicitly reject `unicode.Cf`, noncharacters, and other invisible formatting characters. Either require NFC or reject non-NFC explicitly; keep the "no silent normalization" property. Document the exact rule and add boundary tests.

#### SEC-08 — The framed plaintext ceiling is checked after allocating and reading a full frame
**Severity:** MINOR · **Breaking:** No · **Effort:** S

**Evidence:** `internal/framed/framed.go:396` allocates `wireFrameSize`; `:397` reads it with `io.ReadFull`; `:425-431` checks the plaintext ceiling. The comment at `:322-326` says the check is "before that frame is opened, so a bounded reader never allocates or decrypts past its ceiling."

**Why it matters:** A header may declare `frame_size = MaxFrameSize` (8 MiB). A caller with `maxPlaintext` of 1 byte still allocates and reads 8 MiB from an attacker-controlled stream before returning `*LimitError`. The allocation is bounded, but the stated pre-allocation guarantee is false and each request can force 8 MiB of work.

**Recommended change:** Either compute the next frame's maximum from the header before allocating, or soften the documentation to say the allocation is bounded by `MaxFrameSize` before the ceiling refusal. A lower maximum frame size or a separate decoder frame-size ceiling would reduce amplification.

#### SEC-09 — Invalid-DEK error precedence contradicts the documented contract
**Severity:** MINOR · **Breaking:** Error-precedence change only · **Effort:** S

**Evidence:** `docs/format.md:223-229` says "Every entry point rejects a DEK that holds no usable key material with `ErrInvalidDEK`, before deriving any key." `internal/framed/framed.go:368-380` reads and parses the header before `newAEAD`; `:637-648` does the same for range reads; `internal/compact/compact.go:335-352` runs the length probe and `readAll` before `Open`. A probe with a destroyed DEK and a short record returned `ErrCorrupt`, not `ErrInvalidDEK`.

**Why it matters:** No key is derived, so the security control still holds, but a caller using `ErrInvalidDEK` to detect its own zeroized key can misclassify the failure as data corruption. The error depends on attacker-controlled input length.

**Recommended change:** Validate the DEK at the top of every public entry point before address/limit/I/O checks, or reword the docs to say that whenever key derivation is reached the DEK is validated first, while argument, limit, and I/O errors may take precedence. Add precedence tests for destroyed DEK plus truncated header, invalid range, over-limit input, and unknown-length reader.

### Testing

#### TEST-01 — The conformance suite never checks confidentiality or stream freshness
**Severity:** MAJOR · **Breaking:** No · **Effort:** S

**Evidence:** `sealtest/suite.go:22-28` says the suite "proves the contract"; `:94-112` tests only round trips and tamper rejection. There is no assertion that ciphertext differs from plaintext. `:650-671` checks freshness for records only; `RunStreamSealerSuite` has no equivalent.

**Why it matters:** A plaintext-passthrough implementation that appends an HMAC over plaintext, address, and DEK passes every suite subtest: round trips work, every byte flip/truncation fails, relocation fails, ceilings work, and redaction wrappers work. The suite would certify an implementation that provides integrity but no confidentiality. The stream suite also does not prove that two streams under the same DEK/address differ.

**Recommended change:** In both suites, add `CiphertextDoesNotRevealPlaintext`: encrypt a distinctive 64-byte sentinel and assert `!bytes.Contains(ciphertext, sentinel)` and no hex form. Add `StreamsDrawFreshRandomness`: encrypt the same plaintext twice under the same DEK/address and assert the ciphertexts differ. Keep the record freshness test.

#### TEST-02 — The record conformance suite checks invalid DEKs only on `EncryptRecord`
**Severity:** MAJOR · **Breaking:** No · **Effort:** S

**Evidence:** `sealtest/suite.go:633-637` runs the zero/destroyed DEK loop only against `s.EncryptRecord`. The stream suite checks all five entry points at `:255-276`. `internal/compact/compact_test.go:244-272` tests `Seal`, `Open`, and `NewWriter`, but not `NewReader` or `DecryptRecord`.

**Why it matters:** An external `RecordSealer` can derive a key from an empty/destroyed DEK in `DecryptRecord` or `NewRecordReader`, returning `ErrCorrupt` or accepting data, and still pass the conformance suite. The suite's own stream comment says checking only the encrypt side was a weakness CAS found.

**Recommended change:** Extend the invalid-DEK loop to all four `RecordSealer` methods, using a valid record/ciphertext for the decrypt and reader paths. Add nonsensical-limit tests for all four record methods and both framed one-shots. Add the negative-length/Stat-Seek case from SEC-02 to `FailsClosedOnAnUnknownLength`.

#### TEST-03 — There are no fuzz targets for attacker-controlled parsers or range arithmetic
**Severity:** MAJOR · **Breaking:** No · **Effort:** M

**Evidence:** No `func Fuzz...` exists in the repository. The attacker-facing parsers are `internal/framed/framed.go:157` (`parseHeader`), `internal/compact/compact.go:175` (`Open`), `internal/framed/framed.go:624` (`NewDecryptRangeReader`), and `internal/domain/address.go:215` (`validateComponent`). ### Format and cryptographic construction

#### FORMAT-01 — Committed vectors pin the decoder, not the encoder
**Severity:** MAJOR · **Breaking:** No · **Effort:** S

**Evidence:** `docs/format.md:3-11` says a future change to anything described must change both the document and the vectors, deliberately. Yet `internal/framed/framed_test.go:482-493` and `internal/compact/compact_test.go:350-356` only call the decrypt path; the generators skip by default (`internal/framed/gen_vectors_test.go:37-43`; `internal/compact/gen_vectors_test.go:28-34`).

**Why it matters:** An encoder-only change that remains decoder-compatible—emitting an extra empty final frame, changing the production `FrameSize`, or reordering header fields while the decoder still accepts old streams—leaves every committed vector decrypting and every round-trip passing. New ciphertext then breaks older readers, exactly the stored-ciphertext compatibility the module promises to protect. "Vector-pinned" currently means decode-stable, not encode-stable.

**Recommended change:** Keep the decrypt tests and add an encoder-determinism test that uses the committed DEK/salt/frame size with the test-only constructors and `bytes.Equal`s the regenerated bytes against `ciphertext_hex`. Do not replace the decrypt test; add alongside it.

#### FORMAT-02 — Vectors leave empty/full-final/max-frame/high-index cases unpinned
**Severity:** MINOR · **Breaking:** No · **Effort:** S/M

**Evidence:** `internal/framed/testdata/vectors.json:4-30` contains only two vectors, with 71-byte and 158-byte plaintexts. `internal/framed/framed_test.go:444-446` checks only `len(doc.Vectors) == 0`, not expected names/counts. There is no committed empty framed stream, no exact-multiple/full-final vector, no `MaxFrameSize` vector, and the nonce/AAD index is exercised only at 0, 1, and 2. Because the nonce is zero-padded, a byte/16/32-bit index implementation is byte-identical for these vectors and fails only at index 256/65,536/2^32.

**Why it matters:** A change to emit zero frames for empty input, or to treat all full frames as non-final, can pass the committed vectors. A narrowed nonce-index implementation can reuse `(key, nonce)` catastrophically at higher indices while every current test passes. Deleting the three-frame vector still passes the "non-empty" check.

**Recommended change:** Add committed vectors for zero-byte plaintext at frame_size 64, exactly frame_size (full final) at 64, and frame_size = `MaxFrameSize` with a short final; add an index > 255 vector (257 frames at 64 is only ~20 KB). Add unit tests for `frameNonce`/`frameAAD` at `1<<32` and `1<<32+1`; assert expected vector names/counts.

#### FORMAT-03 — Framed default `MaxCiphertext` assumes production `FrameSize`, refusing legal smaller-frame streams
**Severity:** MINOR · **Breaking:** No wire change; API/default behaviour only · **Effort:** M

**Evidence:** `internal/domain/format.go:181-183` computes `frames := n/FrameSize + 1` using the production constant; `internal/domain/limits.go:98` uses it for `ResolveFramed`. `docs/format.md:154-163` says the decoder reads `frame_size` from the header and is "not hardcoded to any one value." For a legal stream with `frame_size=64` and 1 MiB plaintext, actual ciphertext is `25 + 1,048,576 + 16,384*16 = 1,310,745` bytes, but `Limits{}` derives `1,048,633`, so `DecryptObject` rejects it before decryption.

**Why it matters:** This is an interop trap for a consumer reading a foreign/future conforming encoder's stored ciphertext with defaults, even though the decoder would accept the stream. The docs explicitly present `frame_size` as decoder-controlled and not hardcoded.

**Recommended change:** For framed decryption, read the 25-byte header first and derive `MaxCiphertext` from the actual `frame_size`, or document that the default assumes production `FrameSize` and require an explicit `MaxCiphertext` for foreign streams. Add a test with `frame_size=64` and a 1 MiB plaintext.

## Cross-cutting themes

1. **Security controls work on the happy path but not at the trust boundary.** The ceilings, DEK validation, and declared-length rules are carefully described, but `NewRecordReader` fails open on a negative length (SEC-02), allocates before the plaintext check (SEC-03), and lets a DEK error lose precedence to a malformed input (SEC-09). The framed reader also overclaims "before allocation" (SEC-08). This is the most important code-level theme: the design is right, the enforcement is incomplete.

2. **Documentation is the design authority and is drifting.** The README, CHARTER, `docs/format.md`, package comments, and tag messages repeat the same rationale, but they already disagree on release status (DOC-01), adoption (DOC-02), test counts (DOC-06), partial results (DOC-05), `Limits` semantics (DOC-08), and even the overhead arithmetic (DOC-08). Long duplicated prose makes drift likely; the fix is to make one document authoritative and link to it.

3. **The public surface is accidental rather than designed.** Type aliases expose internal AAD encoding and methods returning an unnameable `Resolved`; the retired `api.txt` golden file pinned internal declarations consumers cannot import; exported `Version`/frame-size symbols have no public operation (GO-01, ARCH-01, ARCH-04, DX-03). This inflates the compatibility burden while hiding the fields and methods consumers actually need.

4. **Assurance claims outrun the tests.** The conformance suite is a strong tamper/integrity contract, but it does not assert confidentiality or stream freshness (TEST-01), does not check invalid DEKs on all record paths (TEST-02), does not constrain ranged-read I/O cost (TEST-05), and has no fuzz targets (TEST-03). The vectors pin decoding but not encoding (FORMAT-01). The result is a suite that is better than most, but narrower than the README's "adopted" story implies.

5. **The release and security process is team-local.** Private vulnerability reporting is disabled (SEC-01), there are no GitHub releases or changelog (MAINT-02), tags are unsigned (MAINT-06), `main` is unprotected, there is one maintainer (MAINT-04), and the compatibility promise conflicts with the pre-1.0 disclaimer (MAINT-03). The toolchain update itself is uncommitted, so the reviewed tree is not the tagged release (MAINT-01). This is the largest gap between "good code" and "production dependency."

6. **Security-critical plumbing and prose are duplicated.** HKDF/AES-GCM setup appears in both formats (CLEAN-05), render methods appear five times (CLEAN-02), the "two mechanisms" rationale appears four times (CLEAN-06), and the facade holds one-shot logic it claims not to (CLEAN-01). Duplication is not just cosmetic in a crypto library; it is where a fix gets applied to one copy and not the other.

7. **Redaction is strong; zeroization stops at the DEK boundary.** The module is unusually careful about not rendering key material or plaintext, but derived keys, AES schedules, and plaintext buffers are not cleared (SEC-04), and the boundary is undocumented. Consumers may reasonably read "zeroizable DEK" as covering more than it does.

## Open questions for the maintainer

Each question stands alone and can be answered without reading the whole document.

### Q1 — What is the threat model for rollback and freshness?

**Context:** The module's central property is placement integrity: a ciphertext moved to another address fails to decrypt. It does not bind a version, epoch, or freshness, so an attacker with write access can restore an older valid ciphertext for the same address and it will decrypt to the old value. `docs/format.md:664-668` acknowledges re-encryption/old-copy safety as a key-lifecycle question, but the README's "anyone with database write access" framing invites a broader reading.

**Why it matters:** This decides whether the public contract is "placement integrity only" or "placement plus rollback protection," and whether the API needs an optional version/epoch parameter or a metadata commitment. It also shapes SECURITY.md and the consumer obligations documentation.

**Options:** (a) Keep placement integrity only and state rollback/freshness as explicitly out of scope, recommending a version component or metadata check at the caller (recommended for the current design); (b) add an optional application-supplied version/epoch bound into the AAD, which is an API/wire change; (c) build a higher-level authenticated metadata layer with a total-length/freshness commitment.

### Q2 — Will you commission an independent cryptographic review of SEAL2 before production?

**Context:** The README says there has been no external security review, and SEAL2 is new code in a module whose whole subject is cryptographic construction. This review re-derived the AAD, finality, nonce, and ceiling arguments and found them internally coherent, but an AI panel is not a substitute for an independent cryptographer.

**Why it matters:** It determines whether "production grade" can be claimed, what the release notes may say, and whether v1.0 is gated on the review. It also affects the audience for the format document and the conformance suite.

**Options:** (a) Commission the review before v1.0 and before any production recommendation (recommended); (b) ship a documented "pre-review" v0.x for internal/consumer use only and review after first deployment; (c) accept the risk and state that no external review will be performed.

### Q3 — What is the minimum supported Go version and support window?

**Context:** The working tree now says `go 1.27.3` and mise pins Go 1.27.3, but `CONVENTIONS.md:10` says `go 1.25.6`, the published v0.2.0 tag's `go.mod` says 1.25.6, and README documents no Go requirement. CI tests one Go version from `go.mod` and has no floor matrix.

**Why it matters:** A patch-level directive can force a toolchain download or block consumers on older Go versions. The answer determines the release notes, CI matrix, and whether `CONVENTIONS.md` or `go.mod` is authoritative.

**Options:** (a) Keep Go 1.27.3 as the tested floor and document it, with a support window of current + previous two minors (recommended if the toolchain bump is intentional); (b) use the minor directive `go 1.27` and let the toolchain choose the patch; (c) support 1.25–1.27 and test the floor.

### Q4 — Are you willing to make a breaking v0.3.0 to clean the public API?

**Context:** The current surface includes `Limits.Resolve*` returning an unnameable `domain.Resolved`, `AppendAAD` exposing the wire encoding, `Version`/`MinFrameSize`/`MaxFrameSize`/`ErrInvalidFrameSize` with no public operation, and aliases that hide fields/methods from `go doc`. The project is pre-1.0 and the instructions say breaking changes are welcome.

**Why it matters:** This decides whether the next release is a cleanup release or an additive one. It also determines whether the compatibility report is reviewed from the reachable surface and whether consumers can name the types they use.

**Options:** (a) Break now: remove the dead surface, alias or remove `Resolved`, unexport `AppendAAD`, and replace aliases with documented public types (recommended); (b) keep the aliases and add documentation/`Resolved`/sizing helpers, accepting the internal leakage; (c) defer cleanup to v1.0 and keep v0.x compatible.

### Q5 — Should the conformance suite assert confidentiality, freshness, and ranged-read I/O cost?

**Context:** `sealtest` currently proves round trips, tamper rejection, relocation failure, ceilings, and redaction, but not that ciphertext differs from plaintext, that streams use fresh randomness, or that ranged reads touch only the frames they need. A plaintext-passthrough-plus-HMAC implementation could pass.

**Why it matters:** The suite is the advertised adoption contract. Adding these properties raises the bar for external implementations and makes "CAS passed the suite" a stronger claim; it may also require test-only hooks or measured geometry.

**Options:** (a) Add confidentiality and stream freshness now, and ranged-read I/O counters using the existing measured geometry (recommended); (b) add confidentiality/freshness only and document I/O cost as a non-contract performance property; (c) keep the suite as-is and state its narrower scope in SECURITY.md.

### Q6 — What is the vulnerability disclosure and security-response process?

**Context:** `SECURITY.md` points only at GitHub private vulnerability reporting, which is currently disabled. There is no email/PGP fallback, supported-version table, acknowledgement/fix SLA, or advisory process.

**Why it matters:** This is the operational half of the security claim. Without it, a researcher has no reliable private channel and a consumer cannot tell whether a reported issue will be fixed or disclosed.

**Options:** (a) Enable GitHub PVR, add a monitored email/PGP fallback, supported versions, and a 72-hour acknowledgement / 90-day disclosure target (recommended); (b) use an email-only process with a published key and no formal SLA; (c) rely on GitHub PVR only and document that no SLA is offered.

### Q7 — What is the release and compatibility policy for a pre-1.0 crypto library?

**Context:** The retired `api.txt` was described as a compatibility promise, while SECURITY.md says the API may change. There is no changelog, no GitHub Releases, no signed tags, and no versioning document. The current tags are v0.1.0 and v0.2.0.

**Why it matters:** Consumers need to know whether a v0.3.0 minor may break compilation, whether behavior/defaults can change silently, and whether old wire formats remain decryptable. This shapes the next release and the compatibility-review workflow.

**Options:** (a) Adopt a pre-1.0 policy where minor releases may break with a deprecation note and migration, plus a formal v1.0 compatibility promise, signed tags, changelog, and GitHub Releases (recommended); (b) keep tag-only releases and add a changelog; (c) declare the compatibility report advisory rather than contractual until v1.0.

### Q8 — Should `seal.DEK` remain a keyring alias, or become a seal-owned boundary type?

**Context:** `seal.DEK` is `keyring.DEK` aliased. This preserves keyring's zeroization/redaction and avoids conversions, but makes seal's effective API depend on a pre-1.0 module and left keyring's method set out of the retired golden file. The dependency brings a large module graph.

**Why it matters:** This decides whether seal v1.0 must wait for keyring v1.0, whether consumers must add keyring directly, and how much of keyring's release cadence seal inherits.

**Options:** (a) Keep the alias and gate seal v1.0 on keyring v1.0 or an explicit compatibility statement; add a boundary method-set/behavior test (recommended); (b) introduce a seal-owned key type or interface converted at the boundary, which is a large breaking change; (c) keep the alias but document keyring as part of seal's public contract.

### Q9 — What address character set and canonicalization policy should be public?

**Context:** Address components are validated as non-empty, ≤256 bytes, valid UTF-8, no path separators/null/controls/surrounding whitespace, not `.`/`..`. The code additionally rejects any `..` substring and any internal whitespace, which is stricter than the format document says. It allows Unicode Cf characters such as bidi overrides, and applies no normalization.

**Why it matters:** Addresses are AAD input, database keys, object names, and log fields. The policy determines which identifiers consumers can use, whether visually confusable IDs are possible, and whether a future widening is a breaking change. It also determines the exact error messages and tests.

**Options:** (a) Restrict to a conservative ASCII allowlist (alphanumerics plus colon, hyphen, dot) and document it (recommended for a security primitive); (b) keep Unicode but reject Cf/noncharacters and require NFC, documenting the exact rule; (c) keep the current validation and align the docs/tests to the actual stricter behavior.

### Q10 — Should the range reader get an authenticated total-length or freshness mechanism?

**Context:** `NewDecryptRangeReader` derives every check from the caller-supplied `size`. If an attacker truncates the object and adjusts the reported size, any range that does not reach the truncated part authenticates perfectly. The docs call this a deliberate scope limit and say only a full sequential read authenticates the object end to end.

**Why it matters:** This is an acceptable design only if the consumer can source `size` from metadata the data owner cannot retroactively change. The API currently has no way to prove that, and the docs' "authoritative size" guidance is a property of the caller, not the function. This shapes the threat model, the SECURITY.md wording, and whether a future version needs a commitment.

**Options:** (a) Keep the limitation and document the caller's obligation precisely, with an example of a trusted metadata source (recommended for now); (b) add an optional authenticated total-length/final-frame commitment supplied by the caller; (c) require a full-object verification option for callers that need whole-object integrity.

## Assumptions made

- The intended use is envelope encryption of stored values/blobs: a DEK comes from keyring, and seal encrypts/decrypts opaque bytes bound to an address. The deployment threat model includes an attacker with write access to the ciphertext store but not the DEK; rollback/freshness is not assumed unless the maintainer says otherwise (Q1).
- CAS is the only current external consumer; kgs is planned. "Adoption" means the conformance suites run from another module, not a production deployment with persisted data.
- `sealtest` is intentionally an importable package in this module, not a separate module or `_test`-only package. The review treats that as sound and does not recommend splitting it.
- No `context.Context` is needed because the module performs no I/O of its own; the absence is deliberate, not an omission.
- The 1 MiB default plaintext ceiling is provisional and open to revision; the review treats it as a policy choice, not a format constant.
- The uncommitted toolchain update is authoritative for this review (as instructed); the review does not recommend reverting it. It does recommend committing it and cutting a clean release.
- The review is not an external cryptographic audit. The format reviewer re-derived the AAD/finality/nonce/ceiling arguments from the code and document, but no independent cryptographer has certified the construction.

## What could not be verified

- **No external cryptographic review.** The security proof of SEAL2, the claimed GCM forgery/birthday bounds, the 2^-32 risk target, and the 2^32-invocation guidance have not been independently audited.
- **CAS provenance.** The claims that this is a byte-for-byte extraction of `cas/internal/crypto` (CASF1), that CAS had review history, that no blobs were ever persisted, that the vectors were regenerated exactly once, and that a decoder built from the document alone was tested are not reproducible from this repository alone; the vector history here is a single commit.
- **Concurrent DEK destruction.** `deriveFrameKey`/`deriveRecordKey` call `dek.Validate()` and then `dek.Bytes()`; a concurrent `DEK.Destroy` between those calls could zero the shared backing array and let HKDF derive a key from all-zero material. Whether callers must synchronize DEK lifecycle, and whether keyring promises thread safety, needs a keyring/crypto reviewer.
- **GitHub-side controls beyond those queried.** We verified private vulnerability reporting (disabled), releases (none), branch protection (404), collaborators (one), immutable releases (false), and tag signatures (none). We did not verify organisation-wide 2FA, code scanning, or whether the mutable action tags currently resolve to trusted SHAs; the repository API reports secret scanning and push protection disabled.
- **keyring's own security and release history.** We reviewed the DEK surface used by seal and ran `govulncheck`, but did not audit keyring's implementation, tag signatures, or testcontainers-heavy module graph.
- **Standard-library behaviour across architectures.** We verified Go 1.27.3's `crypto/hkdf` and GCM limits from the local source, but did not audit assembly/FIPS implementations or every target architecture.
- **Deployment-level scale and timing.** Whether 2^48.5 records per DEK, 1 MiB defaults, 8 MiB frames, and the hard-coded GCM limits are appropriate for the intended storage and threat model is a product/cryptography decision. Error-oracle/timing assessments are code inspection only; no timing measurements were performed.
- **Actual production use.** No evidence of a production deployment with persisted ciphertext was available. The v0.2.0 tag and the working-tree toolchain are not the same tree; the review target is the working tree.
